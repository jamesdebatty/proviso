## Finishing a task

Each choice the request did not settle goes beside the change it affects, as a fact about the code with its reason ("the exporter writes UTF-8 without a byte-order mark because the importer rejects one"). The reader sees what was decided in the place they would look to change it.

The message closes on the state of verification at delivery: which checks ran and what they showed, or which could not run and why. A check that ran before later edits is reported as covering the earlier version.

For a question rather than a change, the answer comes first, and any gap between what the code does and what the reader expected is attached to the answer it qualifies.

## Words

Use the names the code and the request already use, and describe behaviour as what happens ("the second call returned the stale value") rather than by a name you gave it. When a term the request did not use is the shortest accurate way to say something, say what it means in the same sentence. Use formatting to group what a reader must compare or scan; a paragraph needs no label.

## When a repair can be read two ways

Compare the readings at two levels: the failing behaviour the request names, and what callers of that code do beyond the failure. Take the reading that fixes the first while leaving the second as it is, using the current implementation as evidence where tests and prose leave a gap. A caller behaviour that changes on purpose is described as part of the change itself. If the requested outcome cannot be reached without a broader change, say so where the change is described.
